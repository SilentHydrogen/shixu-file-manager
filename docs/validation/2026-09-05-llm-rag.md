## Findings and fixes

- HTTP requests lacked the required `ohos.permission.INTERNET` declaration. The permission check failed before the manifest fix.
- An automatic-protocol URL ending in `/responses/` selected a Chat Completions body. A host test executing the real client with a fake HTTP transport reproduced the response parsing failure. Trailing slashes are now normalized and conflicting explicit protocols rejected.
- Provider errors were replaced with a generic message. The UI now distinguishes authentication, endpoint/model, rate limiting, server, timeout, DNS and certificate failures. Raw provider response bodies and API keys are not included in errors.
- Testing a draft configuration mutated the active service. Testing now uses an isolated client; saving applies the configuration. Input fields bind directly to page state, and save operations cannot overlap from the UI.
- HUKS key generation used the same alias on every save. Existing keys are now reused and generation explicitly forbids overwriting. Encryption completes before preferences are updated.
- Returning from settings did not refresh chat consent. Chat and organize pages refresh on `onPageShow`; the service is also reinitialized after startup configuration loading.
- Embedding input buffers were always INT64. They now follow the actual tensor's INT32 or INT64 dtype and validate its byte size. This is input-type adaptation, not a conversion or verification of model weight quantization.
- Repeated analysis could leave duplicate pending suggestions. New suggestions replace the pending suggestion for that file. Acceptance publishes the classification after file persistence, and the home page synchronizes the result when shown.
- Background RAG enrichment no longer overwrites a rule or manually chosen category. It produces summary, keywords and embedding; category changes belong to the rule engine and explicit review flow.

## Interaction design

1. Import into the inbox and apply existing rules.
2. Configure the provider using its API base/full endpoint, model ID, API key and protocol. Test and save are separate operations.
3. Ordinary conversation sends only typed conversation messages (up to 12 recent messages), without retrieving files. File Q&A retrieves file context and requires the existing file-content consent.
4. File Q&A offers starter questions, source filenames and request retry. Its current service remains one-question-at-a-time retrieval; conversational query rewriting is not implemented.
5. AI organization shows pending suggestions before the file list, including category, confidence and reason. Users accept or reject each suggestion. Low-confidence results are not applied automatically.

Further design work: persist passage-level indexes with source offsets, use the active profile's complete custom category vocabulary, make review/file/database persistence transactional, and evaluate retrieval recall against a maintained document fixture set. These are future work, not validated capabilities of this change.

## First-save keystore fix (device follow-up)

The user reproduced "系统安全存储不可用" on Save. Device HUKS logs at 14:18:37 and 14:19:17 showed `HksKeyExist ... result = -13`. The installed SDK's `isKeyItemExist` Promise documentation explicitly states that absence rejects with `12000011`; unlike the deprecated API, it does not resolve `false`. The previous implementation and host fake incorrectly assumed a false return. As a result, first-time saving stopped before key generation.

`ensureKey` now catches only `12000011` and creates the AES key. Other lookup failures are rethrown as an Error containing the numeric code; existing keys remain reused and overwrite remains prohibited. The host fake was corrected to reject on absence. The check failed with `12000011` before the fix and passes after it, including a separate unexpected IPC-error case verifying that no replacement key is generated.
